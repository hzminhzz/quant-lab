# S05 revision preregistration — HYP-2026-099

Sealed before `RUN-HYP099-001` ran, per spec criterion 6 of
`.workspace/plans/carver_daily_decision/spec.md`. Anything not listed here is
inadmissible: a revision may not be invented after seeing a trial result, and a
threshold may never be lowered to make a revision admissible.

The admissible axes and their objective failure rules are fixed by spec criterion 7.
A revision runs only when the immediately preceding trial row for this hypothesis fails
the axis the revision names:

| Axis | Failure rule |
|---|---|
| `2x_cost_survival` | `stress_2x_cost_sharpe <= 0.50` |
| `latency_survival` | `delay_plus1_sharpe <= 0.0` |
| `breakeven_cost` | `breakeven_cost_bps < 1.0` (0.5 bps taker + 0.5 bps slippage) |
| `param_neighbour_stability` | `param_neighbor_stability < 0.50`, or any `param_grid` point recorded during that trial with annualised net Sharpe ≤ 0 |

Both revisions move the one knob S05 actually has — the EWMAC speed pair. `vol_target`
is deliberately untouched: it scales every weight linearly, so gross return and turnover
scale together and neither Sharpe nor `breakeven_cost_bps` moves. `warmup` stays at 1 in
every trial because it masks a lookback window rather than changing the rule.

Note on what is *not* admissible: a bare `net_sharpe <= 1.0` failure is not in the closed
set, so a trial that simply lacks edge cannot be "revised". In that case S05 closes with
its budget unspent, and the decision record says so.

```yaml
hypothesis_id: HYP-2026-099
contract_id: MULTI_ASSET_1D_V1
revisions:
  - run_id: RUN-HYP099-002
    axis: 2x_cost_survival
    parameters:
      fast: 96
      slow: 384
      vol_span: 35
      vol_target: 0.16
      per_instrument_cap: 0.5
      warmup: 1
    rationale: >-
      Slow both EWMAC speeds by 1.5x. Reversal frequency falls roughly with the
      faster speed, so round-trip cost drag falls while the forecast construction,
      sizing and long-only constraint stay identical. This is the only lever that
      moves cost survival without changing the mechanism.
  - run_id: RUN-HYP099-003
    axis: latency_survival
    parameters:
      fast: 128
      slow: 512
      vol_span: 35
      vol_target: 0.16
      per_instrument_cap: 0.5
      warmup: 1
    rationale: >-
      Slow the speeds again, by 2x versus baseline. One extra bar of execution delay
      costs a fixed amount per position change, so latency drag is proportional to
      turnover; a slower filter holds longer and cuts the number of position changes
      that the extra bar can hurt.
```
